Case study

            
Issue Tracker API

            
A REST API for logging bugs, assigning them to developers and tracking them until they're fixed. I built it over three labs, adding one feature at a time.

            
    
              
  • TypeScript
  • Express 5
  • MongoDB
  • Zod
  • Node.js
    • 
            

          


          

            

              
Problem

              
Software teams need one place to report bugs and follow each one until it's fixed. Without a tracker, bug reports get lost in chat messages, nobody knows who's working on what, and there's no record of whether a fix was ever tested. The API needed to accept bug reports, reject incomplete or invalid ones, and keep each issue's whole history (status, comments, test results) together in one record.

            


            

              
My role

              
I built the whole API myself as a course project:

              
    
                
  • Designed the issue data model in TypeScript: author, assignee, status, classification, comments and test cases.
    • 
                
  • Wrote all 10 Express routes and their controllers.
    • 
                
  • Built a reusable validation middleware that runs any Zod schema and returns field-by-field errors.
    • 
                
  • Moved storage from in-memory arrays to MongoDB in the final lab.
    • 
                
  • Tested every route by hand and recorded the results.
    • 
              

            


            

              
What I built

              
A layered Express app: routes map URLs to controllers, middleware validates requests and attaches the current user, and a data layer talks to MongoDB through the official Node.js driver.

              

                

                  Issue Tracker endpoints
                  
                    
MethodEndpointWhat it does

                  
                  
                    
POST/issuesReport a new bug

                    
GET/issues/:idLook up one issue

                    
PATCH/issues/:idEdit the title, description, steps or priority

                    
PATCH/issues/:id/statusMove it to open, in progress or closed

                    
PATCH/issues/:id/classifyMark it approved, unapproved or duplicate

                    
PATCH/issues/:id/assignAssign it to a developer

                    
POST/issues/:id/commentsAdd a comment

                    
DELETE/issues/:id/comments/:commentIdRemove one comment

                    
POST/issues/:id/test-casesAdd a test case

                    
PATCH/issues/:id/test-cases/:testCaseIdMark a test case passed or failed

                  
                

              

              
Two design decisions matter most here. First, the server sets the author from the signed-in user and ignores any author the client sends, so nobody can file a bug under someone else's name. Second, comments and test cases are updated in place with MongoDB's $push, $pull and array filters, so changing one never touches the others.
